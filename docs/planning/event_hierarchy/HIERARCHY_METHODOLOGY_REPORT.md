# 이벤트 계층 구조 구축 방법론 보고서

> 작성일: 2026-01-29

## 1. 목적

CHALDEAS의 모든 이벤트를 맥락 속에서 이해할 수 있도록 계층 구조로 연결한다.

```
"워털루 전투"를 볼 때:
→ 이게 뭐의 일부지? → 나폴레옹 전쟁
→ 그건 또 뭐의 일부지? → 프랑스 혁명 이후 유럽 격변기
```

**고립된 이벤트 → 연결된 역사**

---

## 2. 기존 접근법의 문제점

### 2.1 LLM 배치 분류기의 오류

**시도한 방식:**
```
이벤트 → LLM → "레벨 2, 부모는 Napoleonic Wars"
```

**문제점:**

| 문제 | 설명 |
|------|------|
| 레벨 선할당 | 레벨은 관계에서 파생되는 것인데 먼저 정함 |
| 일방향 | 부모만 찾음, 자식은 안 찾음 |
| 부모 생성 | 없으면 새로 만듦 (이미 DB에 있어야 하는데) |
| 비재귀적 | 동적/재귀적 트리 구축 고려 안 함 |

### 2.2 근본적 오해

**잘못된 가정:**
- "부모 이벤트가 DB에 없을 수 있다" → Wikidata에서 import 했으므로 있어야 함
- "레벨을 먼저 알 수 있다" → 관계가 먼저, 레벨은 파생
- "카테고리로 필터링" → 전쟁↔혁명↔사회변화 연결되므로 불가

---

## 3. 올바른 방법론

### 3.1 핵심 원칙

```
1. 레벨은 관계에서 파생된다
2. 양방향 탐색: 부모도 찾고 자식도 찾는다
3. 상대적 비교: A > B? A < B? A ≈ B?
4. 트리는 비교에서 자연스럽게 형성된다
```

### 3.2 단일 이벤트 처리 알고리즘

```
이벤트 E 처리 시:

1. 위로 탐색 (부모 찾기)
   - E를 포함하는 더 큰 이벤트가 있는가?
   - 있으면 → E의 부모로 연결

2. 아래로 탐색 (자식 찾기)
   - E에 포함되어야 할 기존 이벤트가 있는가?
   - 있으면 → E의 자식으로 연결

3. 재귀적 검증
   - 부모의 부모는?
   - 자식의 자식은?
   - 전체 트리 정합성 확인
```

### 3.3 비교 기준

**"A가 B의 부모인가?" 판단:**

| 기준 | 설명 | 예시 |
|------|------|------|
| 시간 포함 | A의 시간 범위가 B를 포함 | 나폴레옹 전쟁(1803-1815) ⊃ 워털루(1815) |
| 범위 | A가 B보다 일반적/광범위 | "전쟁" > "전투" |
| 명시적 관계 | Wikidata P361 등 | Battle of X P361 War of Y |

**주의: 카테고리/종류로 필터링하면 안 됨**
```
혁명 → 전쟁 → 조약 → 정치변화
(카테고리를 넘어서 연결됨)
```

### 3.4 대규모 데이터 처리

**문제:** 46,834개 이벤트 전부 비교 불가능

**해결:** 시간 기반 필터링

```sql
-- 이벤트 E(1815년)의 부모 후보 찾기
SELECT * FROM events
WHERE date_start <= 1815
  AND (date_end >= 1815 OR date_end IS NULL)
  AND is_aggregate = true  -- 부모 후보는 aggregate급
```

**필터링 후:** 수만 개 → 수십~수백 개

**비교는 필터링된 후보에 대해서만 수행**

## 5. 구현 계획

### 5.1 Phase 1: 앵커 이벤트 확립

**목표:** 이미 관계가 확실한 이벤트들을 앵커로 삼음

```
1. Wikidata P361 관계가 있는 이벤트들
2. 이미 confirmed 상태인 이벤트들
3. 최상위 aggregate 이벤트들 (World War II, Roman Empire 등)
```

### 5.2 Phase 2: 고아 이벤트 연결

**목표:** 부모 없는 이벤트(unknown)를 앵커에 연결

```
For each orphan event E:
    1. 시간 필터로 부모 후보 추출
    2. 후보들과 비교: "E가 C의 일부인가?"
    3. 맞으면 연결
    4. E도 앵커가 됨
```

### 5.3 Phase 3: 역방향 검증

**목표:** 기존 aggregate 이벤트의 자식 찾기

```
For each aggregate event A:
    1. A의 시간 범위 내 이벤트 검색
    2. 부모 없는 이벤트 중 A의 자식이 될 후보 찾기
    3. 연결
```

### 5.4 비교 방법

**옵션 A: 규칙 기반**
```python
def is_child_of(event, candidate_parent):
    # 시간 포함 여부
    if not (candidate_parent.date_start <= event.date_start
            and candidate_parent.date_end >= event.date_end):
        return False

    # 이름에 부모 언급 여부
    if candidate_parent.title.lower() in event.description.lower():
        return True

    # 같은 Wikidata P361 체인
    if event.wikidata_id and candidate_parent.wikidata_id:
        return check_wikidata_p361(event, candidate_parent)

    return "uncertain"
```

**옵션 B: LLM 쌍별 비교** (uncertain인 경우만)
```
질문: "Battle of Waterloo"는 "Napoleonic Wars"의 일부인가?
응답: Yes/No/Uncertain
```

## 6. LLM 사용 지침

### 6.1 LLM이 해야 할 것

```
✓ 쌍별 비교: "A가 B의 일부인가?"
✓ 불확실한 경우만 호출
✓ 시간 필터 후 소수 후보에 대해서만
```

### 6.2 LLM이 하면 안 되는 것

```
✗ 레벨 할당: "이건 레벨 2야"
✗ 부모 추측: "부모는 아마 X일 거야" (DB에서 찾아야 함)
✗ 새 이벤트 생성: (이미 있어야 함)
✗ 전체 분류: (개별 비교만)
```

## 7. 예상 비용

### 7.1 규칙 기반으로 해결 가능한 경우

- Wikidata P361 있음: ~1,580개 → **무료**
- 시간+이름 매칭: 추정 ~10,000개 → **무료**

### 7.2 LLM 필요한 경우

- 불확실한 경우: 추정 ~20,000개
- 후보당 평균 5개 비교: 100,000 비교
- 비교당 ~$0.001: **~$100**

(기존 배치 분류 $38 대비 증가하지만, 정확도 높음)
